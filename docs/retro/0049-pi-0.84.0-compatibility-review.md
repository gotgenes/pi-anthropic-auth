# Retro: #49 — Verify pi 0.84.0 compatibility before upgrading

## Stage: Final Retrospective (2026-08-07T17:52:22Z)

### Session summary

Reviewed pi 0.84.0 against this package before the host was upgraded, and established empirically that no source changes were required.
Then landed the dev-dependency bump plus three follow-ups — a biome 2.5.x config migration, a lint-driven test refactor, an `AGENTS.md` loader-mode correction, and an `onResponse` pass-through test — and released `v2.0.2`.
A final unrelated task renamed the `claude-opus-4-8` model alias to `claude-opus-5` in two prompt templates.

### Observations

#### What went well

1. **The compatibility question got an empirical answer, not a changelog opinion.**
   Rather than mapping release notes onto our source by inspection, the session bumped devDeps to `0.84.0` and ran the real gates — `tsc --noEmit`, 53 vitest tests, `fallow:dead-code` — then a live CLI repro with `PI_ANTHROPIC_AUTH_DEBUG=all` once the host was upgraded.
   The debug trace showed all three shaping layers still firing: `/compat` transport resolution, the `sk-ant-oat` gate, billing-block injection (2 → 3 `system[]` blocks), and all three prompt-sanitizer anchors matching.
   That converted "probably fine" into a verified answer.

2. **A new test was verified red-first by breaking the source.**
   After adding the `onResponse` pass-through assertion, the session injected `onResponse: undefined` into the delegate call, confirmed the test failed, and reverted.
   This is the first time the session log shows a new assertion proven by mutation rather than assumed to be meaningful.

3. **The tag-source gotcha was followed unprompted.**
   The `AGENTS.md` rule "Diagnose Version Regressions From The Tag Source" (Refs #40) says to diff the upstream clone at both release tags rather than trusting greps or the installed copy.
   The session did exactly that — `git diff v0.83.0 v0.84.0` across `packages/ai/src/types.ts`, `provider-composer.ts`, `extensions/types.ts`, and `extensions/loader.ts` — which is what surfaced the third loader mode and the new documented `streamSimple` contract.

#### What caused friction (agent side)

1. `missing-context` — **Dropped the `registerApiProvider` thread.**
   At turns 15–16 the session grepped the upstream clone and found zero `registerApiProvider` references in `packages/coding-agent/src` at either `v0.83.0` or `v0.84.0`.
   That directly contradicts `AGENTS.md:86` and `docs/architecture.md:28`, which both assert that `registerProvider({ api, streamSimple })` routes through pi-ai's singleton API registry.
   The discrepancy was noticed and then explicitly set aside as "not 0.84-specific, let's not over-scope."
   Open issue #46 reports precisely this gap, with dist-level evidence, and claims background agents consequently bypass the wrapper.
   `gh issue list` was never run during the investigation, so the connection was not made.
   Impact: `v2.0.2` shipped with a disproven mechanism still stated as fact in two documents, and an independently reproduced data point for an open issue went unrecorded.

2. `rabbit-hole` — **Worked around a lockfile error instead of reading it.**
   The first `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` failure at turn 19 printed its own remediation: run `pnpm clean --lockfile` and then `pnpm install`.
   The session instead bypassed the gate by invoking `./node_modules/.bin/tsc` and `./node_modules/.bin/vitest` directly, and only followed the printed instruction at turn 40 — 21 turns later.
   Impact: 12 tool calls across two clusters (turns 18–24 and 37–41) on an obstacle whose fix was in the first error message.

3. `scope-drift` — **Mutated the working tree to answer an advisory question.**
   The opening question was "what, if anything, do we need to update?" and the session answered it by running `pnpm add -D` at turn 18, changing `package.json`, `pnpm-lock.yaml`, and `pnpm-workspace.yaml` without asking.
   The user clarified at turn 27 that they had not upgraded yet and were asking beforehand.
   Impact: a full revert at turn 29 and a re-do of the same bump at turn 37.
   The verification itself was valuable and ultimately kept — the cost was doing it silently rather than flagging it first.

4. `other` — **An empty assistant turn forced the user to repeat themselves.**
   At turn 87 the model produced a response with no content and no tool calls, and the user re-sent the identical request verbatim at turn 88.
   Impact: one wasted round trip.

#### What caused friction (user side)

1. **The advisory framing arrived after the tree had been modified.**
   "I haven't updated pi yet, I'm asking *before* doing so" at turn 27 was the decisive constraint, and it landed nine turns after the dependency bump.
   Stating it upfront would have prevented the revert-and-redo cycle — though the more reliable fix is on the agent side, which should have asked before mutating a clean tree.

2. **Model routing for the mechanical task was sound but hit a reliability failure.**
   Selecting `opencode-go/deepseek-v4-flash` for a two-file find-and-replace was a reasonable cost match.
   It produced an empty turn requiring a verbatim re-send, which is worth weighing when routing future mechanical tasks in this repo.
